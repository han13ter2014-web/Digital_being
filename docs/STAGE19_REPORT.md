# Этап 19 — одно бюджетное решение на попытку действия

**Дата:** 2026-10-24.
**Статус:** завершён; новое поведение выключено по умолчанию.
**Версия Delamain:** `0.12.0`.
**Версия драйвера эффектора:** `0.1.0`.

## 1. Зачем этот этап

Этапы 18A–18B дали ядру контракт эффектора и один шаг за цикл, но расход
энергии оставался размазанным: `DigitalBeing.act()` вычитал стоимость
напрямую, а Delamain исполнял цель без отдельного решения о том, стоит ли
она энергии. Формально бюджет у существа был, однако решения о трате
принимались в разных местах и по разным правилам.

Этап 19 добавляет **одну политику и одну точку решения**: `ActionBudget`.
Она отвечает только на вопрос «можно ли списать стоимость этой попытки
сейчас» и не создаёт второй запас энергии, таблицу, очередь или историю.

## 2. Что добавлено

### 2.1. `src/core/action_budget.py`

* `BudgetDecision` — неизменяемый результат: `allowed`, `action_type`,
  `cost`, `energy_before`, `energy_after`, `reason`, `source`,
  `action_id`, `enabled`, `duplicate`, `capped`;
* `ActionBudget(get_energy, set_energy, ...)` — политика поверх
  существующей энергии агента;
* параметры: `enabled=False`, `min_reserve=5.0`,
  `max_action_cost=20.0`, `essential_actions={"repair", "deep_rest",
  "checkpoint_now"}`, `cache_size=128`;
* `charge(action_type, cost, source=..., action_id=...)` принимает одно
  решение и при разрешении списывает энергию;
* `status()` возвращает политику, счётчики и последнее решение.

Причины решения:

| `reason` | Значение |
|---|---|
| `disabled` | Флаг выключен; действует прежнее списание без новых лимитов. |
| `ok` | Стоимость списана, резерв соблюдён. |
| `essential` | Восстановительное действие прошло ниже резерва. |
| `duplicate` | Эта попытка уже оплачена в этом процессе. |
| `zero_cost` | Нулевая стоимость не требует энергии. |
| `insufficient_energy` | После списания был бы нарушен резерв. |
| `invalid_cost` | Стоимость не число или не конечна; расход отклонён. |

Ключевые свойства:

* при выключенном флаге новые лимиты **не применяются**: это
  сознательное сохранение прежнего `energy -= cost`;
* при включённом флаге обычное действие требует
  `energy >= cost + min_reserve`;
* `max_action_cost` усекает стоимость одной попытки, факт усечения
  виден в `capped`;
* отказ не списывает энергию и не кэшируется: после восстановления та же
  попытка получает новое решение;
* `action_id` кэшируется только для разрешённых попыток, поэтому повтор
  в пределах процесса не списывает энергию дважды;
* нечисловая и не конечная стоимость отклоняются (fail-closed).

### 2.2. `DigitalBeing.act()`

При наличии `agent.action_budget` решение принимается **до** побочных
эффектов, включая `death_risk`-реакцию. При отказе возвращается
`"Ответ: Бюджет не разрешает <action>: <reason>"`, энергия не меняется,
побочный эффект не выполняется. Прямое `self.energy -= cost` убрано из
ветки с бюджетом; без бюджета поведение остаётся прежним.

`DigitalBeing` создаёт `agent.action_budget` из
`config/simulation_config.py` и публикует его снимок в
`get_subsystems_status()["action_budget"]`.

### 2.3. Delamain

`DelamainSubsystem` больше не исполняет попытку цели без бюджетного
решения. `_budget_gate()` вызывается:

* в `_run_goal()` — для обычного и повторного исполнения;
* в `run_pending_goal()` через `_run_goal()`;
* в `run_now()` — ручной путь не обходит бюджет;
* в `approve()` — до `runtime.run_approved()`;
* в `run_effector_pending()` через `_run_goal()`;
* в `DelamainEffectorAdapter.step()` — через исполнение цели.

Идентификатор попытки — `delamain-goal-<id>-attempt-<n>`; для approval без
цели — `delamain-approval-<id>`. Стоимость —
`ACTION_BUDGET_EFFECTOR_COST` (по умолчанию `4.0`). При отказе:

* цель остаётся `pending`;
* эпизод не пишется, энергия не списывается;
* summary содержит `budget_denied=True` и `budget` с решением;
* approval не расходуется и может быть повторён после восстановления;
* перебор целей в тике останавливается, потому что следующая цель имеет
  ту же стоимость.

`DelamainEffectorAdapter.step()` добавляет решение в
`result.detail["budget"]`. `DelamainSubsystem.status()["budget"]` и
`agent.get_subsystems_status()["action_budget"]` показывают текущую
политику.

### 2.4. Конфигурация

```python
ACTION_BUDGET_ENABLED = False
ACTION_BUDGET_MIN_RESERVE = 5.0
ACTION_BUDGET_MAX_ACTION_COST = 20.0
ACTION_BUDGET_EFFECTOR_COST = 4.0
```

## 3. Границы и безопасность

Новых прав нет:

* sandbox не менялся;
* approval не обходится, не дублируется и не расходуется при отказе;
* planner не получает права исполнения;
* нет новой SQLite-таблицы, миграции или индекса;
* нет второго запаса энергии, отдельной бюджетной таблицы, очереди или
  истории;
* `cancel` по-прежнему не реализован: для него нужна единая очередь.

Бюджет — это политика, а не вторая бухгалтерия. Источник истины об
энергии остаётся один — существующий `EnergySubsystem`.

## 4. Что осталось за границей этапа

* **Нет durable-бюджета.** Решения и кэш `action_id` живут только в
  памяти процесса. Перезапуск может списать ту же попытку повторно.
* **Нет транзакции.** Списание энергии и её чекпоинт не атомарны; сбой
  между ними может оставить расхождение.
* **Резерв не резервируется.** Он проверяется в момент решения; два
  последовательных решения не «видят» будущих трат.
* **Нет межпроцессной защиты.** Два одновременных процесса ядра не
  защищены общей транзакцией или unique-индексом.
* **Остановка локальная.** При исчерпании бюджета останавливается
  конкретная попытка и перебор целей в тике, а не весь агент: другие
  действия с иной стоимостью могут быть разрешены.
* **Обычные legacy-цели Delamain** в core-driven режиме по-прежнему
  ждут единой очереди этапа 20.

## 6. Ограничения вывода

Этап проверяет, что бюджетное решение принимается в одной точке и что
отказ не тратит энергию и не выполняет действие. Он **не** доказывает
AGI, сознание, «настоящую жизнь» или экономическую оптимальность.
Успешный тест означает только, что в описанном сценарии политика
сработала предсказуемо. Это измеримый инженерный прогресс, а не
доказательство сильного ИИ.
