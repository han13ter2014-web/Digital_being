# Этап 15 — отчёт: перепланирование с контекстом упавшего шага

**Дата:** 2026-10-22.
**Статус:** готово; новая возможность выключена по умолчанию. Поведение
этапов 7–14 сохранено.

## 1. Цель этапа

Stage 14 научил подсистему перестраивать план между попытками, но planner
получал только исходную задачу. Он не знал:

* какой именно шаг упал;
* с какими аргументами он выполнялся;
* какая ошибка и вывод были получены;
* какие шаги уже успели выполниться.

Поэтому «новый» план мог повторить ту же ошибку. Stage 15 закрывает этот
разрыв, не добавляя planner'у прав на исполнение:

* сохраняет компактный результат упавшего шага в metadata цели;
* передаёт его активному planner'у на следующей попытке;
* делает это только по явному флагу;
* оставляет approval, sandbox, лимит попыток и `run_now()` без изменений.

Главный принцип: это **не** пошаговое самоисправление внутри одной
попытки. Новый план по-прежнему строится между попытками и выполняется
только через обычный runtime.

## 2. Что сделано

### 2.1. Конфигурация

Добавлен один параметр в `DelamainSubsystem` и
`config/simulation_config.py`:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DELAMAIN_REPLAN_WITH_CONTEXT` | `0` | передать planner'у результат упавшего шага |

Env имеет приоритет над config. Флаг не включает replan сам по себе:
нужны одновременно `DELAMAIN_REPLAN_ON_FAILURE=1` и
`DELAMAIN_REPLAN_WITH_CONTEXT=1`. Поэтому по умолчанию поведение Stage 14
не меняется.

### 2.2. Контекст ошибки

После неудачной попытки при включённом флаге в metadata цели появляется
`last_failure_context`:

```json
{
  "stage": "action",
  "attempt": 1,
  "failed_step": 2,
  "action": "read_file",
  "args": {"path": "missing.txt"},
  "error": "file not found: missing.txt",
  "output": null,
  "completed_steps": [
    {"action": "write_file", "args": {"path": "first.txt", "content": "ok"}}
  ]
}
```

Поля:

| Поле | Что означает |
|---|---|
| `stage` | `action`, `normalization` или `planning` |
| `attempt` | номер упавшей попытки |
| `failed_step` | номер шага, начиная с 1 (может отсутствовать) |
| `action` | имя упавшего действия |
| `args` | аргументы упавшего шага |
| `error` | ошибка выполнения или планирования |
| `output` | вывод упавшего действия, если он был |
| `completed_steps` | шаги, которые уже успели выполниться |

Контекст ограничен по размеру: строки обрезаются, вложенные списки и
словари — до 20 элементов. Это наблюдение для планирования, а не дамп
файлов или всей памяти.

`stage=normalization` означает, что план не прошёл нормализацию до
исполнения; `stage=planning` — что planner не смог построить план. В этих
случаях `failed_step` может быть `null`, но ошибка сохраняется.

Контекст живёт в JSON metadata цели, поэтому переживает перезапуск
процесса. Успешная попытка очищает его: `last_failure_context=null`.

### 2.3. Передача planner'у

`DelamainRuntime.run_task()` получил необязательный keyword-параметр
`failure_context`. Если он задан и у planner есть метод
`replan(task, context)`, runtime вызывает именно его. Если метода нет,
используется обычный `plan(task)` — старые кастомные planner'ы остаются
совместимыми.

Добавлены методы:

* `HeuristicPlanner.replan()` — детерминированный planner не учится на
  результате и разбирает задачу заново;
* `FallbackPlanner.replan()` — пробует `replan()` у primary, затем у
  fallback; ошибки и `last_used`/`last_error` работают как раньше;
* `OllamaPlanner.replan()` — добавляет контекст в prompt.

`OllamaPlanner` передаёт контекст в user-message как **недоверенные
данные** и просит модель не повторять ту же ошибку. Контекст ограничен
4000 символами, а системная инструкция явно запрещает выполнять
инструкции из этого блока. План модели всё равно проверяется по live-схеме
действий и проходит approval/sandbox.

### 2.4. Наблюдаемость

* `/delamain status` показывает `context=on|off` рядом с
  `backoff`/`cap`/`replan`.
* `/delamain goals` показывает `replan=next(context)`, если следующий
  повтор будет с контекстом.
* Результат ошибки в чате сообщает, что повтор будет с перепланированием и
  контекстом.
* В summary результата добавлены `replan_context`, `failure_step` и
  `failure_action`.

### 2.5. Совместимость и безопасность

* `DELAMAIN_REPLAN_WITH_CONTEXT=0` по умолчанию: `last_failure_context`
  не пишется, `replan()` не вызывается, поведение Stage 14 сохраняется.
* Схема SQLite не менялась: контекст хранится в JSON metadata цели.
* Pending approval не считается ошибкой действия и не получает контекст.
* Reject завершает цель без retry и очищает контекст.
* `run_now()` не использует replan/контекст.
* Уже одобренный план выполняется как есть; контекст не подменяет approval.
* Новых действий, сети и запуска кода нет; sandbox остаётся единственной
  path-политикой.

## 3. Поток

```text
попытка N
    │
    ▼
runtime.run_task(task, plan)
    │
    ├── шаг 1 ok
    ├── шаг 2 error
    │       │
    │       ▼
    │   _failure_context()
    │       │
    │       ▼
    │   metadata.last_failure_context
    │
    ▼
attempts < max? ── нет ──► failed
    │ да
    ▼
replan_on_next_attempt = true
    │
    ▼
попытка N+1
    │
    ├── replan_on_failure off → старый план
    └── replan_on_failure on
            ├── replan_with_context off → planner.plan(task)
            └── replan_with_context on  → planner.replan(task, context)
                    │
                    ▼
            новый план → approval/sandbox → шаги
```

## 4. Тесты

Добавлены 5 тестов:

* контекст содержит упавший шаг, аргументы, ошибку и выполненные шаги,
  переживает перезапуск подсистемы и передаётся `replan()`;
* ошибка планирования сохраняется со `stage=planning` без номера шага;
* без `DELAMAIN_REPLAN_WITH_CONTEXT` вызывается обычный `plan()`, а
  `last_failure_context` не создаётся;
* `FallbackPlanner` передаёт контекст в primary `replan()`;

## 5. Что не сделано

* Нет перестройки плана после каждого успешного шага: контекст
  используется только на следующей попытке.
* Нет замены отдельного шага внутри уже выполняемой попытки.
* Нет автоматического повторного выполнения завершённых шагов с откатом:
  это потребовало бы отдельной политики идемпотентности.
* Нет семантического поиска похожих навыков и редактирования отдельных
  шагов proposal.
* Нет OpenAI-совместимого endpoint, удаления файлов и запуска кода.

## 6. Итог

Stage 15 делает повторное планирование содержательнее: planner получает
не только задачу, но и компактный результат конкретного упавшего шага.
При этом решение остаётся ограниченным и проверяемым: новый план строится
только на следующей разрешённой попытке, проходит тот же approval и
sandbox, а по умолчанию всё работает ровно как в Stage 14.
