# D6-4 — Сохранение hunt-следа после restart

Дата подготовки: 2026-11-21.

Орган: **Следопыт тем (curiosity)**.
Соседний орган: **Чекпоинтинг**, только для сериализации и восстановления поля.

Основание: решение владельца D6-4 в `MOTIVATION_DECISION_GATE_D6.md`;
контролируемые доказательства D5-06/D5-07 в `MOTIVATION_OBSERVATION_D5.md`.

Статус: **implementation завершён локально и проверен 2026-11-21**; фактические
результаты записаны в `MOTIVATION_HUNT_PERSISTENCE_D6_4.md`. Commit/push не
разрешены этим документом.

## 1. Подтверждённая функциональная проблема

Сейчас `_hunt_misses` хранит `{тема: cycle_count}` последнего неуспешного поиска
и не даёт обращаться к той же теме повторно, пока разница циклов `<200`.

При restart сохраняются открытые вопросы, ментальные модели, активная цель,
needs и `cycle_count`, но `_hunt_misses` после restore пуст. Поэтому тема и
мотивация продолжают прежнюю жизнь, а опыт её неудачной охоты исчезает. В D5-06
контрольный повтор после restore снова вызвал поисковик до истечения прежнего
cooldown.

Владелец выбрал сохранять этот опыт между restart. Цель тикета — устранить
разрыв непрерывности, а не изменить саму политику охоты.

## 2. Цель и нецели

### Цель

Сохранять и атомарно восстанавливать след промахов `web_search` вместе с
остальным состоянием той же жизни, чтобы после restore действовала исходная
граница cooldown.

### Нецели

Не меняются:

- `HUNT_MISS_COOLDOWN_CYCLES=200` и сравнение `<200` / `==200`;
- источники тем, target, кандидаты, top-5, availability и арбитр;
- WorldDelta, valence, curiosity, needs и goal-feedback;
- условия записи miss, очистки следа после success и обработки исключений;
- `_news_reads`, `_web_browses`, `_shared_topics` и другие следы;
- состав сохраняемых вопросов, целей, моделей и needs;
- изоляция новой жизни;
- внешний поиск, сеть, SDK, API и LLM.

Новые лимиты, eviction, нормализация темы или изменение формата значения в этот
тикет не входят.

## 3. Контракт хранения

В checkpoint добавляется необязательное верхнеуровневое поле:

```json
{
  "hunt_misses": {
    "как связаны слои нейросети": 10
  }
}
```

Правила:

1. Ключ `hunt_misses` соответствует in-memory `_hunt_misses` и содержит копию
   отображения, без разделяемой с state изменяемой ссылки.
2. Ключи — непустые строковые темы; значения — целые неотрицательные номера
   циклов. `bool`, float, строки и отрицательные значения не принимаются.
3. Если checkpoint содержит `cycle_count`, номер промаха не может быть больше
   сохранённого текущего цикла.
4. Отсутствие поля является legacy-форматом и означает пустой след `{}`.
5. Применение legacy-checkpoint к агенту с уже существующим `_hunt_misses`
   очищает след, а не смешивает его с состоянием другого момента.
6. Порядок записей не влияет на поведение. Темы не переименовываются и не
   нормализуются при restore.
7. Поле аддитивно и обратно совместимо: `SCHEMA_VERSION` и миграции не меняются
   только ради необязательного поля.

## 4. Минимальный production-diff

После отдельного разрешения implementation ограничивается:

1. `src/core/checkpoint_serializer.py`
   - описать `hunt_misses` в формате checkpoint;
   - включить копию `_hunt_misses` в `build_state_from_agent()`;
   - разобрать и провалидировать поле в фазе 1, до присваиваний агенту;
   - применить staged-значение в фазе 2, включая legacy default `{}`.
2. `src/core/checkpoint_validation.py`
   - добавить side-effect-free валидацию отображения и диапазона циклов.
3. `src/core/agent_creation.py`
   - обновить комментарий, который сейчас намеренно описывает стирание следа;
   - инициализация новой жизни остаётся `{}`.

`agent_handlers.py` менять не требуется: действующий обработчик уже читает
`_hunt_misses` и вычисляет cooldown по восстановленному `cycle_count`.

Любое дополнительное production-изменение выводит работу за пределы тикета и
требует нового согласования.

## 5. Инварианты

- До restart и после restore один и тот же след даёт одинаковый cooldown при
  одинаковом текущем цикле.
- Разница `199` блокирует вызов поисковика; разница `200` разрешает новый вызов.
- Новый miss записывает текущий цикл; success удаляет только след своей темы.
- Search exception, disabled и denied не приобретают нового hunt-поведения.
- Restore остаётся атомарным: ошибка валидации не частично меняет агента.
- Старая жизнь не передаёт след новой жизни.
- Отсутствие поля в старом checkpoint не является corruption.
- Другие checkpoint-поля и их ссылки сохраняют текущую семантику.

## 6. Приёмочная матрица

Все прогоны используют изолированные каталоги в `tmp/`; живой `data/` не
используется.

| ID | Сценарий | Обязательный результат |
|---|---|---|
| H-01 | Round-trip непустого следа | `build_state → validate → apply` сохраняет точное отображение тема → цикл |
| H-02 | Пустой след | Пустое отображение сохраняется и восстанавливается без записей |
| H-03 | Legacy без поля | Restore завершается с `_hunt_misses={}`, включая очистку предварительно непустого состояния агента |
| H-04 | Активный cooldown после restore | При miss в цикле 10 повтор в цикле 209 возвращает cooldown и не вызывает search |
| H-05 | Точная граница после restore | В цикле 210 выполняется ровно один новый search; новый miss переносит след на 210 |
| H-06 | Success после restore | Разрешённый success очищает след только выбранной темы и сохраняет текущий world-evidence |
| H-07 | Другие темы | Cooldown одной темы не блокирует поиск новой темы |
| H-08 | Невалидные значения | Не-dict, нестроковый/пустой ключ, bool/float/string/negative cycle и cycle выше `cycle_count` отклоняются до mutation |
| H-09 | Атомарный rollback | После ошибки restore исходные поля и вложенные объекты агента остаются в прежнем состоянии |
| H-10 | Вторая жизнь | Новый агент не наследует след, вопросы, цель или needs первой жизни |
| H-11 | Соседние следы | `_news_reads`, `_web_browses` и `_shared_topics` сохраняют прежнее поведение |
| H-12 | Настоящий файловый restart | `save_state(force=True) → CheckpointSerializer.load() → apply_state_to_agent()` сохраняет след и cooldown в изолированной жизни |

Для H-04…H-07 вызовы поисковика считаются отдельно от выбора и исполнения
действия. Контрольный прямой `act()` не выдаётся за естественный арбитраж.

## 7. Differential-проверка до/после

На одном и том же изолированном сценарии фиксируются:

1. без restart: поведение до и после изменения должно совпасть;
2. restart до границы: старый код вызывает поисковик, новый код обязан вернуть
   cooldown без вызова;
3. restart ровно на границе: обе версии допускают вызов;
4. legacy-checkpoint: обе версии восстанавливают пустой след;
5. success, exception, disabled и denied: изменений вне целевой сохранности нет;
6. second life: изоляция одинакова до и после.

До implementation сохраняется текущий baseline. После него сравниваются сырые
результаты, а не только итоговые assertions.
