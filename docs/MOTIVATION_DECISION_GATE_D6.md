## 1. Правила gate

Для каждого пункта владелец выбирает один исход:

- **оставить** — текущее поведение признаётся приемлемым в наблюденном объёме;
- **наблюдать дальше** — сначала нужен отдельный test-only пакет наблюдений;
- **отдельный implementation-тикет** — формулируется конкретная функциональная
  проблема, но сама ревизия, commit и push этим решением не выполняются.

Исторические записи D5-08 не приравниваются к контролируемым прогонам. Одного
примера или человеческой аналогии недостаточно для ревизии.

## 3. Принятые последствия

По решениям D6-3 и D6-5 следующий пакет D6-R должен:

1. использовать только test-only инструменты и изолированные каталоги в `tmp/`;
2. отдельно считать предложения, выборы, исполнения, сетевые вызовы, cache hits
   и cooldown-ответы;
3. записывать WorldDelta, needs до/после и происхождение кандидата;
4. для D6-3 наблюдать длительные серии естественных повторов и конкуренции;
5. для D6-5 отдельно проверить реальную сеть и релевантность без живого профиля;
6. фиксировать `not_observed`, если честный сценарий недоступен.

По решению D6-4 отдельный implementation-тикет должен определить:

- функциональную проблему потери опыта промаха после restart;
- минимальный набор сериализуемых полей и инварианты изоляции жизней;
- поведение активного cooldown после restore и точную границу 200 циклов;
- regression, differential, restart и second-life проверки;
- полный regression и статические гейты для последующего production-diff;
- отдельные разрешения на implementation, commit и push.

Этот документ сам не создаёт D6-R или implementation-тикет и не разрешает
изменять код.
