# Этап 14 — отчёт: bounded backoff и перепланирование после ошибки

**Дата:** 2026-10-22.
**Статус:** готово; новые возможности выключены по умолчанию. Поведение
этапов 7–13 сохранено.

## 1. Цель этапа

После этапа 9 упавшая цель могла повториться на следующем разрешённом
`tick`, но:

* повтор происходил без задержки;
* повторялся тот же explicit/skill-план, даже если ошибка была вызвана
  именно этим планом;
* состояние повтора было видно только как `attempts` и
  `retry_scheduled`.

Этап 14 закрывает этот разрыв, не добавляя нового планировщика:

* вводит **ограниченный экспоненциальный backoff**;
* хранит время следующей попытки в metadata цели, поэтому расписание
  переживает перезапуск;
* по явному флагу **перепланирует** задачу на повторе через активный
  runtime planner;
* оставляет approval, sandbox и лимит попыток без изменений.

Главный принцип: это не бесконечное самоисправление. Число попыток
по-прежнему ограничено `DELAMAIN_MAX_ATTEMPTS`, а новые возможности не
включаются сами.

## 2. Что сделано

### 2.1. Конфигурация

Добавлены три параметра в `DelamainSubsystem` и
`config/simulation_config.py`:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DELAMAIN_RETRY_BACKOFF_SEC` | `0` | базовая пауза; `0` сохраняет поведение этапа 9 |
| `DELAMAIN_RETRY_BACKOFF_MAX_SEC` | `300` | верхняя граница паузы |
| `DELAMAIN_REPLAN_ON_FAILURE` | `0` | строить новый план на повторе |

Env имеет приоритет над config. Значение `max < base` не создаёт
некорректное расписание: cap поднимается до base. При `base=0` задержка
не создаётся.

### 2.2. Backoff

Задержка вычисляется по формуле:

```text
delay = min(base * 2^(attempt_number - 1), cap)
```

Для `base=60`, `cap=300`: 60, 120, 240, 300, 300…

После неудачи, если попытки ещё остались:

* `status` остаётся `pending`;
* `attempts` увеличивается;
* `retry_delay_sec` содержит рассчитанную паузу;
* `next_retry_at` содержит UTC ISO-8601 время следующей попытки;
* `retry_scheduled=true`.

`run_pending_goal()` фильтрует pending-цели по `next_retry_at`. Пока время
не наступило, цель не выполняется, но другие готовые цели не блокируются.
Если timestamp повреждён, цель считается готовой: ошибка metadata не должна
навсегда «запирать» задачу.

При `DELAMAIN_RETRY_BACKOFF_SEC=0` поле `next_retry_at` не создаётся, и
повтор снова доступен на следующем tick — ровно как в этапе 9.

### 2.3. Перепланирование на повторе

При включённом `DELAMAIN_REPLAN_ON_FAILURE` после ошибки в metadata
ставится `replan_on_next_attempt=true`. Следующая попытка:

1. игнорирует сохранённый `metadata.plan`;
2. не переиспользует skill-план;
3. вызывает активный runtime planner заново;
4. выполняет новый план через тот же `ActionRegistry`, approval и sandbox.

Если planner не смог построить план, это обычная ошибка попытки: она
учитывается в `attempts`, и при остатке попыток снова планируется replan.
Никаких дополнительных прав или обхода approval не появляется.

Перепланирование не выполняется для `run_now()`: это немедленный ручной
вызов вне очереди целей. Pending approval также не считается ошибкой
действия и не запускает backoff/replan. Reject завершает цель как `failed`
без повтора.

### 2.4. Наблюдаемость

В metadata цели добавлены/обновляются поля:

| Поле | Что означает |
|---|---|
| `attempts` | номер завершённой попытки |
| `retry_scheduled` | будет ли ещё попытка |
| `retry_delay_sec` | рассчитанная пауза |
| `next_retry_at` | когда цель снова готова к запуску |
| `replan_on_next_attempt` | следующий запуск должен строить новый план |
| `last_attempt_replanned` | была ли текущая попытка перепланирована |
| `replan_count` | сколько раз реально запускался replan |

`/delamain goals` показывает `retry_at=...`, `replan=next` и
`replanned`, а `/delamain status` — текущие `backoff`, `cap` и
`replan=on|off`. Ошибка выполнения в чате сообщает, когда будет повтор и
будет ли он с перепланированием.

### 2.5. Совместимость

* `DELAMAIN_MAX_ATTEMPTS=1` (значение по умолчанию) — одна ошибка сразу
  переводит цель в `failed`, как в этапе 8.
* `DELAMAIN_RETRY_BACKOFF_SEC=0` и `DELAMAIN_REPLAN_ON_FAILURE=0` —
  поведение этапа 9 без изменений.
* Схема SQLite не менялась: новые поля живут в JSON metadata цели.
* Успешный план по-прежнему сохраняется в `skills`; неудачная попытка
  увеличивает `failure_count`, но не стирает последний успешный план.
* Approval остаётся preflight-барьером для всего плана.

## 3. Поток

```text
цель pending
    │
    ▼
run_pending_goal ──► next_retry_at в будущем? ── да ──► пропустить
    │ нет
    ▼
replan_on_next_attempt?
    ├── да  → metadata.plan = None, skill = None, вызвать planner
    └── нет → explicit plan / skill plan / planner
    │
    ▼
runtime.run_task
    │
    ├── approval pending → ждать решения, без retry
    ├── ok               → done, очистить retry-поля
    └── error
            ├── attempts < max → pending + backoff + replan?
            └── attempts = max → failed
```

## 5. Что не сделано

* Нет перепланирования по результату отдельного шага: planner получает
  задачу между попытками, а не частичный результат упавшего шага.
* Нет jitter и отдельного фонового таймера: расписание проверяется на
  обычном `tick` по wall-clock времени.
* Нет бесконечного retry: лимит `DELAMAIN_MAX_ATTEMPTS` остаётся главным
  ограничителем.
* Нет автоматического approval: опасный новый план по-прежнему ждёт
  пользователя.
* Нет семантического поиска похожих навыков и редактирования отдельных
  шагов плана.

## 6. Итог

Stage 14 делает повторяемость действий честнее: система не долбит одну и
ту же ошибку на каждом tick, умеет ждать и, если это явно разрешено,
попробовать новый план. При этом ядро остаётся детерминированным,
наблюдаемым и ограниченным, а опасные действия не получают обхода
существующего approval.
