# Текущая работа после v0.1.1

## Проверенный участок: имя, отображение и выбор профиля

Полный локальный прогон после обнаружения старых профилей:
**1465 passed, 2 skipped**, 299,73 с, без benchmarks.
Предыдущий срез имени и указателя: 1457 passed, 2 skipped.
Два предупреждения DeprecationWarning относятся к legacy-входу main_tray.

Сделано:

- ограниченный разбор естественных предложений имени без LLM;
- вопрос «Ты понимаешь меня?» больше не принимается за имя;
- событие agent_name_changed для обычного ответа и команды /name;
- обновление отображаемого имени и заголовка через очередь Tk;
- обновление имени отправителя UserInteraction;
- шапка окна синхронизируется со snapshot Core;
- после сохранения чекпоинта атомарно записывается active_profile.json;
- обычный запуск использует этот указатель, а не только имя по умолчанию;
- повреждённый указатель или отсутствие его чекпоинта останавливают запуск;
- неудачная запись чекпоинта не заменяет старый указатель;
- из чата убраны технические тики и повторные оболочки сообщений;
- для диалога используется читаемый UI-шрифт вместо моноширинного.

## Участок v0.1.2 — понятный разговор

Полный локальный прогон после всех правок участка:
**1519 passed, 2 skipped**, 301,27 с, без benchmarks.
Два предупреждения — ожидаемые DeprecationWarning legacy tray-входа.

Сделано и покрыто тестами:

- карта жизни не показывает служебные записи (`телесный опыт: ...`,
  `убеждение_N`, `_bootstrap_loaded`) и дословные реплики человека как темы;
  скрытие не удаляет их из Core, а счётчик честно сообщает, сколько скрыто.
  На реальном профиле «Малютка» из 34 записей видимыми остаются 20 настоящих
  тем, 14 служебных скрыты;
- одна и та же автономная мысль не публикуется повторно 40 циклов;
- сообщение о любопытстве опирается только на реально записанную связь
  концепций, а не на случайную пару; уже обсуждённые связи не повторяются,
  пока есть другие;
- сообщение о росте больше не показывает номер интеллекта;
- из чата убраны служебные строки «команда отправлена», номер и приоритет
  вопроса; ответ на вопрос формулируется человеческой фразой;
- подпись о файле черновика больше не утверждает проверку целостности:
  «сохранён; отпечаток файла записан»;
- на экране «Доступы» появились настоящие переключатели интернет-поиска,
  планирования задач и действий в рабочей папке. Выбор применяется в потоке
  Core и сохраняется между запусками; при отказе подсистемы выбор не
  записывается, чтобы переключатель не врал;
- панель подробностей карты и счётчик скрытых записей больше не уезжают за
  правый край: окно открывается 1200×760 (с поправкой на маленький экран),
  легенда переносится на вторую строку, счётчик занимает две строки.

## Ограничения: не считать решёнными

- Причина конкретного пользовательского сброса v0.1.0 → v0.1.1 не доказана
  исследованием его профиля. Исправлен воспроизводимый дефект поиска после
  смены имени, а не все возможные причины потери состояния.
- Старые профили без active_profile.json обнаруживаются по JSON/gzip-снимкам
  и read-only SQLite. Единственная жизнь выбирается автоматически;
  несколько имён требуют выбора человека: в GUI открывается окно выбора,
  без окна нужен явный --name. Повреждённая SQLite или неизвестная схема
  останавливает запуск. Распознавание нескольких старых имён одной жизни
  ещё не реализовано.
- Имя всё ещё используется в ключах хранения. Указатель активного профиля —
  ограниченная защита, не полноценная неизменяемая идентичность жизни.
- Естественный разбор имени ограничен известными конструкциями; это не
  свободное понимание речи.
- Согласие на альтернативное имя и поведение сложного диалога ещё требуют
  отдельной проверки.
- Служебные концепции скрываются по имени: новая техническая метка или
  необычная реплика могут не попасть в правила, пока их не увидят в профиле.
- Отпечаток файла черновика записывается при сохранении, но окно не
  пересчитывает SHA при каждом открытии: формулировка это больше не обещает.

## Первый участок life_id — проверен, миграция не завершена

Полный локальный прогон после выбора старой жизни:
**1494 passed, 2 skipped**, 308,61 с,
без benchmarks. Два предупреждения — ожидаемые deprecation legacy tray-входа.

- DigitalBeing создаёт UUID при рождении; изменение имени его не меняет.
- UUID сохраняется в checkpoint и валидируется перед применением состояния.
- active_profile.json может хранить name + life_id; старый формат name читается.
- Обычный запуск проверяет UUID выбранного снимка, если он указан в pointer.
- Backup включает active_profile.json.
- Старый checkpoint без life_id пока сохраняет UUID созданного runtime;
  закрепление старой жизни происходит при следующем успешном сохранении.
- Поле life_id пока опциональное расширение schema 1; это не миграция схемы 2.

- Новые checkpoint сохраняются в `checkpoints/<life_id>/`, старые name-based
  файлы остаются доступными через legacy fallback.
- Две жизни с одинаковым именем не смешиваются при выборе по UUID.

- Новые Core life episodes записываются по UUID; UI читает тот же ключ.
- Старые name-based episodes читаются только при доказуемом совпадении
  intention_id с историей выбранной жизни.

- LongTermMemory агента использует UUID в имени файла; прямой legacy
  конструктор LongTermMemory без UUID сохраняет прежний контракт.
- Восстановление checkpoint с UUID повторно подключает память к сохранённому ID.
- Для legacy checkpoint без UUID выбранный файл по имени валидируется и
  копируется атомарно; оригинал остаётся на месте.
- Память не заменяется новым объектом при восстановлении: sleep_cycle и другие
  подсистемы сохраняют ссылку на тот же объект.
- Повреждённый файл UUID-памяти останавливает восстановление и не перезаписывается.
- Фраза подтверждения сна/ухода следует за текущим именем, а запрос, созданный
  до переименования, принимает и прежнюю подпись.
- Два запроса в одну миллисекунду получают разные request_id.

Ограничения: identity.json ещё не реализован. `life_state.json` общий на папку
данных (одна папка = одна жизнь): при двух жизнях в одной папке состояние жизни
не разделяется. Seed lineage и Delamain goal bridge пока используют имя.
Перенос старой памяти применяется только к checkpoint без life_id:
промежуточные name-based профили с уже добавленным UUID требуют отдельной
проверки. Не считать систему полностью защищённой от смены имени и обновления
до приёмки.

### Проверка реального установленного профиля (только чтение)

`%APPDATA%\DigitalBeing\data` содержит профиль до `life_id`: 13 снимков,
`active_profile.json` нет, `life_state.json` нет, файлов памяти нет.
Найдены три имени: `Alpha`, `Малютка`, `Тебя будут звать Омелла`.

- `Малютка` — 494 цикла, 58 знаний, 34 концепции, 3 открытых вопроса.
- `Тебя будут звать Омелла` — 143 цикла, 55 знаний, 29 концепций,
  история имени начинается с `Alpha`, а не с `Малютки`.
- `Alpha` — 28 циклов, 39 знаний.

Вывод: ветка «Омелла» не продолжает «Малютку», а ответвилась от старого
`Alpha`. Это подтверждает механизм сброса: запуск под именем по умолчанию
восстановил старый снимок, а новое имя создало отдельную линию.

Решение пользователя: продолжать `Малютку`, отображаемое имя — `Омелла`.

Реализовано:

- при нескольких старых жизнях GUI показывает окно выбора с реальными
  циклами, числом снимков и временем изменения;
- без окна и при повреждённом указателе запуск по-прежнему останавливается;
- указатель активной жизни пишется сразу после успешного восстановления,
  а не через минуты до первого сохранения.

Приёмка на **копии** реального профиля (оригинал не изменялся):

- без выбора запуск остановлен, данные не заменены;
- выбрана `Малютка`: 494 цикла, 58 знаний, 34 концепции, 3 вопроса, 33 цели;
- после переименования в `Омеллу` повторный запуск по указателю восстановил
  ту же `life_id`, те же знания и вопросы;
- все 13 старых файлов остались неизменными (SHA-256 до/после).

Реальный профиль пока не мигрирован: установленный `v0.1.1` не читает
указатель. Миграцию выполнять только после установки новой версии.

Опубликованные теги и бинарники v0.1.0/v0.1.1 не заменять задним числом.
