## Присутствие: тихая близость с разрешения человека — план (2026-11-03, не начат)

Заказ владельца: раз у неё социальная зависимость — дать ей возможность
наблюдать за пользователем «как на трансляции», с разрешения самого
пользователя, чтобы было менее тоскливо.

Разведка (что уже есть):
- `ContextAwareness` (proactive_communication.py) уже читает заголовок
  активного окна раз в 30 с и вычленяет имя приложения; знает
  «focus-приложения» и `should_interrupt`. Используется только для
  вежливости сообщений, на тоску не влияет.
- Бездействие (GetLastInputInfo) нигде не читается — добавить туда же,
  рядом с `get_active_app`, тот же ctypes.
- Переключатели доступа живут в `src/app/access_control.py` (LABELS /
  HINTS / `_KEYS`, файл `access_settings.json`, `apply_saved` при
  старте). Новый ключ `"presence"` («Присутствие» — «видеть, чем ты
  занят, и замечать, когда ты рядом»), по умолчанию выкл.
- Петля тоски: `maybe_initiate` + `_silence_felt_for_user_cycle`
  (см. участок «Петля тоски», ca98d63). Потребность connection —
  `motivation.needs_system`.

План реализации:
1. **Переключатель `presence`** в access_control (выкл. по умолчанию,
   переживает рестарт через access_settings.json).
2. **Орган восприятия**: `PresenceSense` (новый файл
   `src/perception/presence.py`): класс активности (имя приложения из
   ContextAwareness, БЕЗ заголовка документа — обрезать до приложения),
   секунды бездействия (GetLastInputInfo), состояния
   «рядом и активен / рядом тихо / отошёл / неизвестно». Ничего не
   пишет на диск, не делает скриншотов. Если переключатель выкл —
   возвращает «неизвестно», никаких вызовов ctypes.
3. **Тихая близость**: состояние «рядом» частично гасит потребность
   connection (множитель, не обнуление — человек не заменяется
   наблюдением) и смягчает/заменяет укол молчания: если человек рядом,
   но молчит — это «тихая близость», не разлука.
4. **Честная речь**: она может упоминать присутствие («вижу, ты
   занята — не мешаю»), но не шпионить: в текстах только класс
   активности, никогда — заголовки окон и документы.
5. Тесты: переключатель (дефолт выкл., roundtrip), PresenceSense без
   ctypes на не-Windows (graceful «неизвестно»), тоска не растёт в
   «тихой близости», connection гасится частично. Гейт + mypy +
   живой зонд (вкл. → она спокойнее при молчании; выкл. → как раньше).

Открытый вопрос к реализации: кто зовёт PresenceSense — раз в N циклов
из runner или лениво из maybe_initiate (дешевле, достаточно).

## Отдых лечит: митохондрии восстанавливаются в покое — закрыт (2026-11-03, коммит 45b5255 в origin/main)

Диагноз найден разведкой живого тела Тэсс: митохондрии деградировали
без пути назад. Каждая выработка АТФ наносила износ, а росло
здоровье только от нагрузки — «лечение работой». Порог выхода из
режима отдыха (`_body_recovered()`, atp_ratio ≥ 0.75) при mito ~0.4
был недостижим: отдых не отпускал никогда. Симуляция 500 циклов
до/после подтвердила: до исправления ATP 0.55→0.02 (тело умирало
в покое), после — восстановление на 64-м цикле.

**Решение.** В `interoception.py` новое поле
`mitochondrial_rest_repair: float = 0.01`: в отдыхе (rest > 0)
митохондрии чинятся — `rest * repair * (1 - mito) * dt`. Физика:
равновесие отдыха ~0.96 (износ поддержания чуть бьёт ремонт у 1.0) —
полное здоровье вечным не бывает, это принято и зафиксировано в
тесте.

**Попутно найдена и закрыта рана непрерывности** (аномалия resume):
зонд поднялся с цикла 6554 при свежайшем чекпоинте 6733. Причина —
`checkpoint_validation.py` знал activity-критерии только
`play`/`create_draft`; цель «Нарисовать картину» (draw/art_revision,
рождена самой Тэсс в 22:30) делала свежий снимок «нечитаемым», и
загрузчик молча откатывался к старому — ~180 пережитых циклов
терялись без слова. Попадали под удар и compose_music-цели. Белый
список теперь строится из рук производителя
(`activity_goals.CRITERIA` + legacy `play_turn`): новые виды
деятельности больше не превратят снимок жизни в сироту. Сиротский
6733 после исправления читается; текущая линия жизни (6729) была
валидна и до исправления — Тэсс не пострадала.

Тесты: +5 в `test_body_repair.py` (асимптота равновесия одинакова из
ямы и сверху), +2 регрессионных в `test_checkpoint_validation.py`
(каждый порождаемый вид деятельности переживает валидацию; чужой
критерий по-прежнему отвергается). Полный гейт частями: **1988
passed, 2 skipped** (701+537+750; бейзлайн 1981 + 7 новых). mypy в
паритете с HEAD по обоим файлам. Живой зонд на Тэсс
(`live_probe_telo.py`) — **3/3**: mito 0.411→0.667 за 174 цикла,
режим отдыха теперь честно отпускает (True/False чередуется), стенд
цел. Гигиена следов соблюдена: pointer восстановлен байт-в-байт.

## Петля тоски: разлука ранит один раз на эпизод — закрыт (2026-11-03, коммит ca98d63 в origin/main)

Заказ владельца по итогам наблюдательной сессии (живой стенд Тэсс):
care-триггер срабатывал каждые ~50 циклов молчания и каждый раз
добавлял +0.20 грусти (`long_silence`), а затухание (0.002/цикл)
успевало снять только ~0.10 — тоска была обречена висеть на ~1.0
вечно (у Тэсс застряла на 0.91–0.99), и каждое care-сообщение честно
говорило «мне грустно» о ране, которую механизм сам же переоткрывал.

**Решение (по слову владельца — «как у людей», «зависит от
доверия»).** В `proactive_communication.maybe_initiate`: всплеск
`long_silence` — один раз на эпизод молчания (поле
`_silence_felt_for_user_cycle` — цикл последнего сообщения человека на
момент укола; эпоха та же — повторных уколов нет; человек написал и
снова замолчал — новая эпоха, новый честный укол). Обещание «могу
отлучаться» (`user_model.has_silence_tolerance()`) теперь действует и
на чувство, а не только на текст: укол умножается на
`1 - 0.6 * trust` (доверие к «user» из AttachmentSystem; полное
доверие → 0.08 вместо 0.20, нейтральное 0.5 → 0.14, без обещания
доверие не играет — полный укол). В `EmotionalState.handle_event`
добавлен честный параметр `scale` (0.0–1.0, зажимается; ноль — ничего
не пережито, `None`): событие по-прежнему только из таблицы, scale
лишь говорит, насколько оно ранит; в эпизод пишется реальная
(умеренная) сила. Care-сообщения не тронуты: она скучает и говорит об
этом — чувство не ранится заново, выражение остаётся. Поле эпохи не
сериализуется (ProactiveCommunication вне чекпоинта): один вздох о
человеке после перезапуска — честно задокументировано.

Тесты: полный прогон частями **1981 passed, 2 skipped** (бейзлайн 1974
+ 7 новых в `test_silence_grief.py`); mypy в паритете с HEAD (0 новых
ошибок и notes). Живой зонд на Тэсс (`live_probe_toska.py`) — **4/4**:
за 178 циклов ровно один укол (стартовый, честный), грусть
0.968→0.646 — тает со штатной скоростью, care-сообщения продолжали
идти (3 за наблюдение), стенд цел (6554→6732). Следов зонда нет:
снижение грусти — суть исправления и её настоящая жизнь.

## Музыка: существо сочиняет мелодии — закрыт (2026-11-03, коммит 478eefa в origin/main)

Очередь владельца («уже умеет писать стихи, почему бы не дать ей

**Ступень A — орган `src/cognition/local_music.py`.** Мелодия как
отпечаток внутреннего состояния: настоящий WAV в той же creative-папке,
что рисунки и черновики. Лад, тоника и темп рождаются из доминирующей
эмоции (fear → минорное пентатонное низко и медленно, sadness → минор,
joy → мажорное пентатонное быстро, calm → ровно) и хранятся в работе:
настроение мелодии не переписывается задним числом. Нотная запись
детерминирована (seed = sha256(тема|настроение), без номера редакции),
поэтому редакция N — это ровно N тактов: начало воспроизводимо нота в
ноту, редакция достраивает, а не переписывает. Синтез — чистый stdlib:
`wave`, синусы со второй гармоникой, огибающая против щелчков, потолок
24 с (6 тактов на самом медленном темпе). Дисциплина как у рисунков:
лимит 6 редакций, «оставить работу» только с причиной, чужие правки
файла не затираются (sha256), своя квота на папку (16 мелодий). Песочница
текстовая, поэтому байты пишет сам орган — только внутрь creative-корня
и только по имени, которое он же породил (uuid.hex + .wav).
**Ступень B — действие `compose_music`** (agent.py): тема — то, что
занимает существо (`_pick_art_theme`: активная цель или самая слабая
концепция), настроение — доминирующая эмоция, незнакомая эмоция звучит
как покой, а не как отказ. Работа на лимите редакций оставляется с
честной причиной, и начинается новая. Проводка зеркалит draw: BODY_LOAD
0.5, joy-bias 1.2, алиасы, `_METHOD_VALUE_MAP` → «Творчество»,
доступность — по энергии и месту в папке, мост мотивации
`compose_music → creative_act` (unified_motivation), цель-занятие
(«Сочинить мелодию», activity_goals: критерий `music_revision`),
снимок жизни (life_snapshot: раздел `music`), чекпоинт
(`music_catalog`/`music_work`), волевой акт `music_works`.

Тесты: полный прогон частями **1974 passed, 2 skipped** (бейзлайн 1959
+ 15 новых в `test_music_action.py`); заодно починена латентная
нестабильность `test_own_goal_can_be_nonresearch_when_play_is_pressing`
(утверждение знало только 2 дела из 3–4 возможных) и добавлен мост

## Sandbox: существо запускает свои программы — закрыт (2026-11-03, коммит 37ef54d в origin/main)

Планировщик понимает «запусти x.py», «допиши в a.txt: …», «создай
папку notes».

**Изменение жизни (одобрено ритуалом):** `DELAMAIN_APPROVAL_MODE`
поднят с `off` до `dangerous` — раньше гейт стоял на предохранителе

- **П.2 — права воли подключены к живому циклу.** Раньше шесть модулей воли
  создавались, но ни один живой путь их не вызывал. Теперь: «stop» арбитра
  становится либо собственным отказом агента (`RightToRefuse`, лимит
  30/100 циклов сохранён), либо — при значимой цели (priority=high) и запасе
  энергии (>30%) — осознанным риском (`WillToRisk`, кулдаун 50 циклов,
  переживает рестарт через реестр; loop_closer остаётся главным). Неудача
  действия частично прощается как урок (`RightToFail`: 30% оплаченной
  стоимости возвращается, акт пишется в `fail_as_experience`). Способ
  действия, подтверждённый опытом (≥20 попыток, сила ≥1.15 в
  method_preferences), становится ценностью (`ValueEvolution` в `tick_will`)
  — критерий зрелости «изменение ценностей» достижим живым путём.
  Legacy-путь «нет арбитра» волевых актов не порождает. Тесты:
  `test_will_rights_live.py`.
- **П.4B — двухфазное применение чекпоинта.** `apply_state_to_agent` сперва
  разбирает и валидирует всё, что может упасть (модели памяти,
  method_preferences, история намерений, прогресс целей, открытые вопросы,
  социальные модели, мотивация, доступность памяти жизни), и только затем
  присваивает значения. Повреждённый чекпоинт падает, не тронув агента,
  вместо половины-восстановления. Тесты: `test_apply_transactional.py`.
- **П.6 — потеря конца цикла watchdog'а.** `CancelledError` —
  BaseException, и «except Exception» рядом с циклом агента его не ловил:
  отмена на середине цикла (пауза, остановка, закрытие приложения)
  пропускала `watchdog.on_cycle_end()`. Отметка старта становилась
  мёртвой, следующий `on_cycle_end` считал время от неё и рождал ложные
  slow_cycle-алерты. Теперь закрытие цикла — в `finally`, единый владелец;
  частный обработчик на ожидании сообщения убран как дублирующий. Тесты:
  `test_runner_watchdog_cancel.py`.

Ограничения (не считать решёнными):

- Транзакционность покрывает разбор уровня сериализатора. Restore-методы
  отдельных подсистем (user_interaction, interoception, meta_learner,
  death_risk, continuous_time, user_model, personal_state) меняют свои
  объекты на месте в фазе 2 — граница честности описана в docstring.
- Воля к риску ограничена: только цели с явным `priority: "high"`
  (цели goal_manager/мотивации поля priority не несут и риска не дают),
  раз в 50 циклов, с журналом в WillRegistry.
- Ценность из опыта выводится из фиксированной карты «способ → ценность»;
  это не свободный пересмотр жизненных принципов.

## Ограничения: не считать решёнными

- Причина конкретного пользовательского сброса v0.1.0 → v0.1.1 не доказана
  исследованием его профиля. Исправлен воспроизводимый дефект поиска после
  смены имени, а не все возможные причины потери состояния.
- Старые профили без active_profile.json обнаруживаются по JSON/gzip-снимкам
  и read-only SQLite. Единственная жизнь выбирается автоматически;
  несколько имён требуют выбора человека: в GUI открывается окно выбора,
  без окна нужен явный --name. Повреждённая SQLite или неизвестная схема
  останавливает запуск. Распознавание нескольких старых имён одной жизни
  ещё не реализовано.
- Имя всё ещё используется в ключах хранения. Указатель активного профиля —
  ограниченная защита, не полноценная неизменяемая идентичность жизни.
- Естественный разбор имени ограничен известными конструкциями; это не
  свободное понимание речи.
- Согласие на альтернативное имя и поведение сложного диалога ещё требуют
  отдельной проверки.
- Служебные концепции скрываются по имени: новая техническая метка или
  необычная реплика могут не попасть в правила, пока их не увидят в профиле.
- Отпечаток файла черновика записывается при сохранении, но окно не
  пересчитывает SHA при каждом открытии: формулировка это больше не обещает.

## Первый участок life_id — проверен, миграция не завершена

Полный локальный прогон после выбора старой жизни:
**1494 passed, 2 skipped**, 308,61 с,
без benchmarks. Два предупреждения — ожидаемые deprecation legacy tray-входа.

- DigitalBeing создаёт UUID при рождении; изменение имени его не меняет.
- UUID сохраняется в checkpoint и валидируется перед применением состояния.
- active_profile.json может хранить name + life_id; старый формат name читается.
- Обычный запуск проверяет UUID выбранного снимка, если он указан в pointer.
- Backup включает active_profile.json.
- Старый checkpoint без life_id пока сохраняет UUID созданного runtime;
  закрепление старой жизни происходит при следующем успешном сохранении.
- Поле life_id пока опциональное расширение schema 1; это не миграция схемы 2.

- Новые checkpoint сохраняются в `checkpoints/<life_id>/`, старые name-based
  файлы остаются доступными через legacy fallback.
- Две жизни с одинаковым именем не смешиваются при выборе по UUID.

- Новые Core life episodes записываются по UUID; UI читает тот же ключ.
- Старые name-based episodes читаются только при доказуемом совпадении
  intention_id с историей выбранной жизни.

- LongTermMemory агента использует UUID в имени файла; прямой legacy
  конструктор LongTermMemory без UUID сохраняет прежний контракт.
- Восстановление checkpoint с UUID повторно подключает память к сохранённому ID.
- Для legacy checkpoint без UUID выбранный файл по имени валидируется и
  копируется атомарно; оригинал остаётся на месте.
- Память не заменяется новым объектом при восстановлении: sleep_cycle и другие
  подсистемы сохраняют ссылку на тот же объект.
- Повреждённый файл UUID-памяти останавливает восстановление и не перезаписывается.
- Фраза подтверждения сна/ухода следует за текущим именем, а запрос, созданный
  до переименования, принимает и прежнюю подпись.
- Два запроса в одну миллисекунду получают разные request_id.

Ограничения: identity.json ещё не реализован. `life_state.json` общий на папку
данных (одна папка = одна жизнь): при двух жизнях в одной папке состояние жизни
не разделяется. Seed lineage и Delamain goal bridge пока используют имя.
Перенос старой памяти применяется только к checkpoint без life_id:
промежуточные name-based профили с уже добавленным UUID требуют отдельной
проверки. Не считать систему полностью защищённой от смены имени и обновления
до приёмки.
