# SQLite-снимки без двадцати полных копий памяти

## Первый шаг миграции

Добавлен opt-in backend `sqlite` для обычного `save_state` и восстановления.
В `config/simulation_config.py` `SIM_CONFIG.CHECKPOINT_BACKEND` пока `json`:
переход не должен незаметно менять хранилище уже живущего существа.
После резервной копии каталога данных можно явно выбрать `sqlite`.

Файл: `checkpoints/life.sqlite3`. Снимок имеет ссылку
`life.sqlite3#snapshot=<id>`; штатный latest_checkpoint ищет последнее
SQLite-сохранение указанного имени, затем старые JSON. Если выбран SQLite,
новое сохранение после загрузки старого JSON записывается в базу;
оригинальные файлы не удаляются. При наличии обеих историй SQLite имеет
приоритет: после переключения обратно на JSON нужно явно выбрать снимок,
иначе обычный старт продолжит SQLite-историю.

## Как устроено

SQLite WAL, транзакция на снимок. Таблица snapshots хранит имя, цикл,
время и корневую ссылку. Таблица blobs хранит неизменяемые части состояния
по SHA-256 содержимого. Неизменившиеся части используются разными снимками.
Переживания — отдельные записи; списки разбиты на блоки по 128 ссылок.
Добавление одного переживания не создаёт копию всего старого списка.

Чтение проверяет хеши, отсутствие блоков и допустимую структуру. Запись,
публикация корня и удаление старых ссылок-снимков — одна транзакция.
Хранится максимум MAX_CHECKPOINTS ссылок на агента, а не 20 полных копий.
У разных имён независимое удержание снимков. ID — не граница авторизации.

Пустое best_fitness метаобучения хранится как null вместо невалидного
JSON -Infinity; восстановление оставляет исходное «ещё не измерено».
Числовые ключи state приводятся к строкам как в прежнем JSON roundtrip.
Случайные NaN/Infinity в других данных не замалчиваются.

Штатный runner и выход main не экспортируют полную mental_models.json
при выборе SQLite. Явный экспорт, UI-команды экспорта и семена остаются
JSON для переносимости. Они могут быть большими и ещё не потоковые.

## Обслуживание

```powershell
python tools/manual/checkpoint_maintenance.py data/checkpoints/life.sqlite3 --import-json data/checkpoints/Agent_cycle_100.json
python tools/manual/checkpoint_maintenance.py data/checkpoints/life.sqlite3 --gc
```

Импорт проверяет обратное чтение; исходник сохраняется. GC удаляет только
блоки, недостижимые из всех удерживаемых снимков всех имён. Проверка
целостности предшествует удалению. GC явный, не выполняется при каждом
сохранении. Поэтому удаление старого снимка не сразу освобождает его
уникальные блоки. Освободившиеся страницы переиспользуются SQLite; уменьшение
самого файла требует отдельного VACUUM. Для резервной копии работающей
WAL-базы использовать SQLite backup, а не копирование одного .sqlite3.

## Измеренный результат: 10 000 записей, 20 снимков

| Метрика | JSON | SQLite |
|---|---:|---:|
| Размер всех файлов после закрытия соединений | 111 220 050 байт | 8 572 928 байт |
| Суммарная запись | 0,700 с | 3,412 с |
| Чтение всех снимков | 0,942 с | 3,381 с |

SQLite в 12,97 раза меньше, но медленнее на этом тесте. В базе 10 179
блоков, включая 10 019 уникальных записей опыта. 20 снимков с добавлением
одной записи на шаг; все проверки старейшего/последнего снимка прошли.
WAL/SHM после закрытия отсутствовали; измеритель учитывает их при наличии.
Это синтетический опыт, не миллиард записей и не долгий срок эксплуатации.

## Чего это пока НЕ решает

Каждое сохранение всё ещё строит полный state, нормализует JSON и
обходит/хеширует его. Загрузка восстанавливает всю память в RAM.
Операции чтения/записи не стали O(новые записи). Миллиарды записей не
поддержаны одним фактом использования SQLite.

Первый срез этапа 6: Core теперь явно пишет завершённые intentions в
существующий Delamain MemoryStore, если runtime подключён. Запись append-only,
с life_id/intention_id/action/target/status/outcome; без runtime скрытая память
не создаётся. Technical Effector episodes не превращаются автоматически
в autobiographical events. Профильный core-life/delamain/effector набор: 25 passed. Общий прогон
на границе минимального этапа 6: **1366 passed, 2 skipped**, без benchmarks,
303,80 с. Exactly-once
при аварии не заявляется. Добавлен индекс `idx_episodes_life` по task/life_id/id
и hard-capped pagination recent_life_episodes; адресный memory/index/core
набор: 10 passed. Это ограничивает retrieval page, но не решает retention,
архив, инкрементальную запись всего опыта или рост общей таблицы.

Следующие шаги: append-only журнал опыта, нормализованные сущности и индексы,
инкрементальные dirty-записи, постраничное/ленивое чтение, горячий рабочий
набор и холодный архив. Затем резервное копирование/восстановление и замеры
на возрастающих объёмах. Сжимать/забывать опыт без явно заданной семантики
и проверки сохранения происхождения нельзя.

## Измерение

`tools/manual/checkpoint_storage_measure.py` сравнивает JSON и SQLite
на одинаковой растущей синтетической памяти: размер, время записи/загрузки,
обратное чтение. Результат конкретного объёма нельзя экстраполировать на
миллиарды записей. Тесты хранилища: test_sqlite_checkpoint_store.py;
интеграция/совместимость: test_checkpoint_backend_integration.py.
