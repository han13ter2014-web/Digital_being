# Лонгитюдный журнал состояния и пользовательский экспорт

Дата контракта: 2026-11-22.

Статус: **Core, Tk и Web реализованы; профильные проверки и полный regression
пройдены**. Документ не подтверждает наличие записей в существующих жизнях и не
заменяет проверку на живой Тэсс после отдельного разрешённого запуска.

## 1. Назначение и границы

Журнал принадлежит существующему органу **«Журнал жизни»** (`body_plan.md`, слой 0).
Он должен сохранять наблюдаемое развитие одной сущности и позволять владельцу
выгрузить его без помощи разработчика. Позднее независимый инструмент сможет
сопоставить экспорты разных сущностей.

Журнал помогает исследовать как благоприятное развитие, так и устойчивые неблагоприятные
контуры. Он учитывает кандидатов из `body_plan.md`: руминацию по кольцу, аффективную
петлю зависимости и ангедонию. Сами по себе записи не доказывают ни один из этих
контуров.

Разрешено:

- read-only собирать уже существующие наблюдаемые состояния и эпизоды;
- записывать sanitized-снимки в per-life SQLite;
- экспортировать локальный ZIP с машиночитаемыми данными и автономным HTML-отчётом;
- явно показывать неполноту, ошибки writer и ограничения интерпретации.

Не разрешено этим этапом:

- ставить автоматические медицинские или психиатрические диагнозы;
- называть грусть, ностальгию, усталость или необычное поведение болезнью;
- провоцировать страдание ради наполнения журнала;
- менять эмоции, награды, цели, память, арбитр, речь или выбор действия;
- автоматически «лечить» сущность или подавлять состояние ради красивого отчёта;
- включать сырые диалоги, тексты творческих работ, пути, секреты или чужую память;
- копировать живую SQLite или останавливать сущность ради экспорта;
- сравнивать сущностей без учёта возраста, режима времени, личной базы, конфигурации
  и версий кода.

Различим три уровня: **наблюдение**, **сигнал для исследования**, **интерпретация
человека**. Третий уровень не вычисляется Core и не сохраняется как факт.

## 2. Источник и изоляция

Источником снимков служит существующий read-only `build_life_snapshot()`, а источником
эмоциональных эпизодов — уже созданные `EmotionalState.episodes`. Новый collector
применяет собственный whitelist и не сериализует UI snapshot целиком.

Записи хранятся только в `data/lives/<life_id>/life.sqlite3`, в существующей таблице
`metric_samples`. Миграция `LifeDatabase`, общий JSONL для разных жизней и новый орган
не нужны. Каждая запись проходит через `LifeDatabase` с уже проверенным UUID владельца.

Standalone-профиль без managed `LifeDatabase` не получает скрытый общий журнал. Его
status должен честно сообщать `unavailable`, а не подменять историю глобальным файлом.

## 3. Схема v1

`journal_schema_version = 1`, `export_schema_version = 1`.

### 3.1. `wellbeing.observation`

Одна запись содержит UTC `observed_at`, `cycle`, режим времени и разделы:

- `body`: энергия, усталость, АТФ и другие числовые/булевы показатели из whitelist;
- `emotions`: уровни известной палитры и координаты смеси без словесных причин;
- `motivation`: числовые потребности и разрешённые агрегаты;
- `behavior`: машинные коды текущего и последнего действия, статусы и счётчики;
- `hardware`: только sanitized доступность, свежесть и числовые показатели без путей,
  идентификаторов устройств и истории входных данных;
- `hormonal_projection`: уровни проекции и личной базы, если они доступны;
- `goals`: агрегированные статусы без названий и описаний;
- `data_quality`: отсутствующие разделы и ошибки чтения.

Неизвестные строки не копируются. Машинные коды допускаются только по whitelist либо
после строгой проверки формата; произвольный текст заменяется на `other`/`unknown`.
Числа должны быть конечными; NaN и Infinity запрещены.

### 3.2. `wellbeing.episode`

Сохраняются наблюдаемые связи, доступные Core:

```text
cycle + event code → emotion code + intensity
```

Это не искусственно сконструированная цепочка «причина → состояние → действие → исход».
Если действие или исход в исходном эпизоде отсутствуют, поля остаются `null` с явным
`completeness = partial`; связь не выдумывается. Слова пользователя и произвольные
`cause` не сохраняются.

Эпизоды проверяются каждый цикл, а не только в момент периодического снимка. Дедупликация
не должна стирать два действительно разных эпизода одного типа в одном цикле.

### 3.3. Ошибки и пропуски

Writer fail-open относительно жизни. Ошибка не отменяет tick, остановку или сохранение,
но видна в `AgentRunner.get_status()` как `state_observation_journal.last_error` со
счётчиком пропусков. История не обрезается автоматически.

Если gap-запись удалось сохранить, она получает имя `wellbeing.gap`, UTC-время, цикл и
машинную причину без текста исключения. Если само хранилище недоступно, отсутствие
записи обозначается runtime status и ограничением следующего экспорта.

## 4. Периодичность и полнота

- Первый доступный цикл создаёт наблюдение.
- Далее наблюдение создаётся каждые 30 циклов; повторный вызов для того же цикла не
  дублирует запись.
- Новые эмоциональные эпизоды сохраняются между периодическими наблюдениями.
- Экспорт запрашивает свежий снимок у Runner, после чего читает согласованный срез
  SQLite в read-only транзакции. Если свежий снимок недоступен, экспорт возможен только
  с явным `fresh_snapshot = false` и ограничением `fresh_snapshot_unavailable`.
- Старые записи не удаляются и не переписываются. Sampling не называется полной
  биографией: отчёт показывает число наблюдений, границы циклов и обнаруженные gaps.

## 5. ZIP-экспорт

Пакет содержит ровно следующие обязательные файлы:

| Файл | Содержимое |
|---|---|
| `manifest.json` | `life_id`, период, схемы, версии кода/конфигурации, режим времени, единицы, counts, SHA-256, completeness |
| `observations.jsonl` | sanitized наблюдения тела, эмоций, мотивации и поведения |
| `episodes.jsonl` | наблюдаемые эмоциональные эпизоды и фактически доступные связи |
| `interventions.jsonl` | реальные вмешательства и последствия; при отсутствии источника пустой файл |
| `report.html` | автономный отчёт без сети и внешних скриптов |

JSONL — UTF-8, один валидный JSON-объект на строку, каноническая сериализация с
`allow_nan=False`. Manifest хранит SHA-256 и размер каждого остального файла. Сам manifest
не содержит собственного hash. ZIP не включает SQLite, WAL, checkpoints или raw dialogue.

Если источника interventions пока нет, manifest содержит
`interventions.status = "unavailable"` и `count = 0`. Пустой файл не означает, что
вмешательств не было. Пустая история observations получает `readiness =
"insufficient_data"`, а не нулевое «здоровье».

Отчёт содержит:

- период и фактическую плотность наблюдений;
- графики энергии/тела и отдельных эмоций без сведения палитры к одной оценке;
- таблицу эпизодов с машинными причинами;
- сигналы только как повод для исследования, без диагнозов;
- заметные предупреждения о sampling, gaps, stale и недоступных разделах;
- пояснение, что проекция тела/гормонов — модель, а не медицинское измерение.

Экспорт записывается через временный файл и атомарную замену в выбранный владельцем
путь либо в зарегистрированный artifact текущей жизни. Web-download разрешает только
конкретный зарегистрированный ZIP, а не произвольный путь.

## 6. Пользовательский сценарий

В Tk и Web должна быть команда **«Экспорт состояния»**. Она не требует терминала и не
останавливает жизнь. Пользователь получает ZIP и понятный `report.html`.

По умолчанию пакет sanitized. Отдельный экспорт сырых диалогов этим этапом не
реализуется: добавить его можно только после самостоятельного явного выбора владельца
и отдельного privacy-контракта.

Интерфейс попарного сравнения не входит в этап. `life_id`, schema/config/code versions,
возраст в циклах и режим времени уже присутствуют, чтобы будущий comparison tool не
смешивал несопоставимые биографии молча.

## 7. Приёмочные проверки

1. Две managed-жизни имеют независимые записи и экспорты.
2. Повторный tick того же цикла не дублирует observation; эпизоды не теряются между
   30-цикловыми снимками.
3. Ошибка writer не меняет решения и не останавливает жизнь; status показывает сбой.
4. В SQLite и ZIP отсутствуют контрольные сырые фразы, пути, тексты работ и чужие ID.
5. Фильтр периода не смешивает записи вне диапазона.
6. JSONL валиден, counts и SHA-256 совпадают с фактическими файлами.
7. Экспорт не меняет эмоции, цели, память, выбор или награды.
8. Пустая/повреждённая/неполная история даёт `insufficient_data` или явное ограничение,
   а не видимость полной биографии.
9. HTML открывается локально без сети и не исполняет внешние ресурсы.
10. Tk и Web экспортируют один и тот же Core-формат без второго диагностического
    механизма.

Проверка экспорта выполнена на изолированных managed-жизнях во временных каталогах,
не путём экспорта живой Тэсс. Сквозной Web-тест прошёл маршрут HTTP → EventBus →
Runner → SQLite → Runtime → Web result → скачанный ZIP и подтвердил `life_id` и
`fresh_snapshot = true`.

- Полный regression: **4174 passed, 2 skipped за 542,76 с**. Mypy entry points,
  JavaScript `node --check` и `git diff --check` также прошли.
- Regression запускался с временным `DIGITAL_BEING_DATA_DIR`, но существующий тестовый
  guard всё равно сообщил об изменении `active_profile.json`, `pending_messages.json`
  и SQLite/WAL текущей жизни в рабочем `data/`. Эти файлы не откатывались и не
  перезаписывались; предупреждение не скрывается и не выдаётся за полную изоляцию suite.
- Живая Тэсс не перезапускалась. Live-поведение новых социальных исправлений и
  наполнение журнала в её существующей жизни этими проверками не подтверждаются.
