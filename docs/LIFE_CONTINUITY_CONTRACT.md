# Этапы 0–1: контракт непрерывности и безопасный запуск

## Правила, определяющие дальнейшую работу

- Один профиль данных предназначен одной жизни; разные имена чекпоинтов
  сами по себе не обеспечивают изоляцию отношений, LifeGuard и Delamain.
- Сохранённая история не является новой жизнью при ошибке её чтения.
- Новая жизнь допускается при отсутствии истории либо явном new/restore=False.
- Намерение, исполнение, наблюдение и достигнутая цель — разные события.
- Пауза и остановка приложения не должны обозначаться необратимым уходом.
- Основной чекпоинт — согласованный снимок уже включённых в него полей.
  Пока он не сохраняет всю индивидуальность: ценности, отношения, модели
  действий и другие выявленные пропуски предстоит подключить отдельно.
- JSON и SQLite — способы хранения, а не основания изменения опыта.
- Никакое расширение доступов не включается автоматически этим этапом.

## Первый реализованный участок: восстановление

Запуск перечисляет снимки нужного имени от новых к старым. Сохраняется
прежний приоритет SQLite перед JSON. Перечисление SQLite использует read-only
соединение и не создаёт/мигрирует схему. В JSON-кандидаты входят только
законченные .json/.json.gz, не временные файлы.

Если снимок не читается, проверяется следующий. Отчёт содержит
recovery_failures и recovered_from_older. Исходники не удаляются и не
карантинируются перемещением: оператор сохраняет доступ к повреждённым данным.
Если все снимки не читаются, возникает RecoveryRequiredError; приложение
не получает нового агента для запуска и автоматического сохранения.

Нечитаемая база, неподдерживаемая версия контейнера, более новая версия
состояния либо ошибка применения прекращают запуск. Ошибка применения
особенно важна: apply_state_to_agent пока не транзакционен для всего объекта,
поэтому продолжать подбор на частично изменённом агенте небезопасно.

Убрано безусловное knowledge.save() из bootstrap до восстановления.
Конструктор всё ещё инициализирует подсистемы и может создавать журналы:
гарантия здесь — не стартовать новую жизнь/не перезаписать снимки при
ошибке, а не полное отсутствие любых файловых операций во время запуска.

## Второй реализованный участок: постоянные пути профиля

setup_environment фиксирует абсолютный DIGITAL_BEING_DATA_DIR до создания
агента. В frozen режиме ресурсы остаются в _MEIPASS, изменяемые данные —
в пользовательской постоянной папке. Относительный override разрешается
до chdir. В исходниках корень ресурсов определяется по размещению проекта,
а не по sys.argv[0] (pytest, внешний launcher, установленная команда).
create_agent также привязывает окружение к переданному AppEnv до конструктора.
NurseryWatcher получает тот же data_path(nursery), что создание семян.

Тесты test_profile_paths.py проверяют разделение ресурсов/профиля,
динамические Settings, смену cwd и путь LifeGuard/Яслей реального агента.
Профильный прогон после изменения: 48 passed. Это моделирование frozen
окружения, не испытание реально собранного .exe. Автоматического переноса
данных из прежних ошибочных каталогов нет; существующие файлы не удаляются.
Одновременно менять профиль уже работающего агента нельзя: data_path
по-прежнему использует процессное окружение, а не отдельный StorageContext.

## Третий участок: проверяемый резервный комплект

`src/memory/profile_backup.py` создаёт комплект checkpoints/mind/memory/
nursery/delamain и knowledge_base/life_state/life_requests/life_events.
SQLite распознаётся по заголовку и копируется через backup API, включая
подтверждённые WAL-записи; побочные WAL/SHM не копируются отдельно.
Контроль целостности базы проверяется до публикации. Manifest хранит размеры
и SHA-256; staging-папка публикуется только после проверки всего комплекта.
При ошибке отдельного файла частичный комплект не объявляется успешным.
LifeGuard использует этот путь вместо copytree с подавлением ошибок.

Восстановление проверяет manifest и копирует только перечисленные файлы
в новую папку; существующий профиль не перезаписывается. Это ещё не
автоматическое переключение работающего приложения на восстановленный профиль.

```powershell
python tools/manual/profile_backup.py create ПАПКА_ПРОФИЛЯ НОВАЯ_КОПИЯ
python tools/manual/profile_backup.py verify НОВАЯ_КОПИЯ
python tools/manual/profile_backup.py restore НОВАЯ_КОПИЯ НОВЫЙ_ПРОФИЛЬ
```

Перед созданием комплекта нужно остановить приложение/записи. SQLite backup
обеспечивает согласованность отдельной базы, **не общую транзакцию нескольких
баз и JSON**. В manifest эта граница отмечена. Копия не защищена от
злонамеренной одновременной подмены файлов; ссылки отклоняются, но файловая
изоляция ОС не реализована. Настраиваемые внешние пути Delamain вне профиля
в этот комплект не входят. Логи/кэши и произвольные пользовательские проекты
не включаются автоматически. Хеши — контроль повреждения, не подпись доверия.

Тесты test_profile_backup.py: активный WAL → backup → restore → чтение;
повреждение → отказ до создания назначения; ошибка копирования → отсутствие
опубликованного частичного комплекта; существующий профиль не перезаписывается.
Профильный прогон backup/life_guard/paths/recovery: 32 passed.

## Проверка восстановления жизни из копии

`tests/test_backup_life_continuity.py` проходит путь реального агента:
контролируемое телесное наблюдение → save_now → backup → restore в новую
папку → setup_environment/create_agent. Четыре случая: JSON/SQLite ×
бодрствование/сон. Сравниваются полная ментальная модель и утверждения,
энергия, усталость, цикл, кулдаун и состояние LifeGuard. В бодрствующем
случае следующее действие использует отрицательное ожидание энергии и
положительное ожидание снижения усталости. Сон остаётся сном; действие
не запускается. Исходные файлы не меняются, pending trial не становится
наблюдением. Реестры подсистем сбрасываются между объектами теста: это
имитирует отдельные процессы и не заявляет решённую многопрофильность.

Замер до исправления: 4 из 4 случаев не сохраняли точное совпадение модели.
Причина — прямые присваивания confidence в bootstrap в обход свидетельств:
при восстановлении значения закономерно пересчитывались. Теперь создание
тоже использует recompute_confidence. Старую произвольную уверенность без
оснований не возвращаем; шкала и пороги свидетельств не меняются.
После исправления: 4 из 4 случаев проходят, 46 профильных тестов проходят.
Проверка ошибочных/пустых/повторных путей manifest добавлена отдельно.

## Предварительная валидация и сообщение о восстановлении

validate_checkpoint_state проверяет сериализованные секции до изменения
агента: память/утверждения, цели/прогресс, числовые состояния, социальные
перечисления, мотивацию и метаобучение. Отсутствующие legacy-поля допустимы;
ошибки содержат путь к полю. create_agent проверяет каждый кандидат до
load_state, поэтому читаемый JSON с некорректной поздней секцией может быть
пропущен ради предыдущего снимка без частичной мутации.

apply_state_to_agent также вызывает проверку для прямых потребителей API.
Это защита от известных ошибок входных данных, **не полная транзакция
произвольных методов подсистем**: непредвиденная ошибка при применении
по-прежнему останавливает запуск. Полное staging/publish состояния остаётся
незавершённым. Схема миграций — отдельный следующий участок.

main обрабатывает RecoveryRequiredError для обычного и maturity-json
запуска: сообщение в stderr, код 3, без регистрации atexit-save и без
запуска runner. Рекомендуется сохранить профиль и проверить копию, а не
использовать --new как способ «починить» историю. Отдельного GUI-диалога
восстановления пока нет; в сборке без консоли stderr может быть невидим.

Профильный прогон validator/serializer/recovery/messages/backup/restart:
110 passed. Предыдущий общий прогон до этого участка: 1103 passed, 2 skipped.

## Строгие миграции формата

migrate_state работает на глубокой копии и маркирует версию только после
успешного шага. Отсутствующий мигратор, его исключение, несловарный результат,
неожиданный скачок версии и неправильный тип schema_version — явные ошибки.
Более новая схема не считается повреждением: запуск останавливается и не
откатывается молча на старую жизнь. Правило одинаково для JSON и SQLite.
Исходный словарь и файлы не меняются при ошибке. Текущая версия остаётся 1;
выдуманной миграции 0→1 нет. Legacy без определённой цепочки требует явного
решения по преобразованию, а не автоматической смены номера версии.

Проверки: идемпотентность актуальной схемы, полная последовательная цепочка,
отказ при пропуске/ошибке/скачке и сохранение входа. Интеграционно проверено,
что future schema останавливает запуск обоих backend. Профильный прогон:
89 passed (migrations/validation/recovery/messages/backup/backend).

## Координированная остановка и возобновление

Runtime теперь наблюдает не только shutdown-событие, но и завершение задач
EventBus/AgentRunner. Ошибка runner сохраняется в `runtime.error`, вызывает
остановку остальных задач и даёт ненулевой код приложению. При остановке
сохранение выполняется в потоке жизни через `runner.save_now()`; главный
поток больше не делает дополнительную запись после таймаута. Если поток не
завершился, приложение сообщает ошибку и не делает запись из чужого потока.

Завершившийся runtime передаёт окну `request_close()` через его потокобезопасную
очередь; Tk уничтожается только Tk-потоком. Это устраняет путь «раннер уже
умер, окно осталось». Тесты не запускают настоящий Tk mainloop, но проверяют
границу очереди.

Dormant-состояние LifeGuard не считается окончательным завершением: runner
остаётся в ожидании и может принять wake. Это пока не полноценный UI-сценарий
пробуждения из остановленного `run_forever`; его end-to-end проверка остаётся
отдельной задачей.

Профильный прогон runtime/UI/entry/life: 83 passed. Полный общий прогон
после этой правки: 1183 passed, 2 skipped (без benchmarks), 388,86 с.

## Реальное окно и координация копии раннером

`tools/manual/gui_lifecycle_measure.py --report PATH` и вариант `--tray`
проверены в отдельных процессах с временными профилями и реальным Tk.
Оба: exit_code=0, runtime_finished=true, root_destroyed=true,
saved_on_stop=true, checkpoint_readable=true, error=null. В варианте tray
иконка создана. Проверяется автоматический запрос выхода через runtime,
не физический клик каждого элемента меню и не установленный .exe.

Open Chat теперь передаёт show в очередь окна; runtime останавливает
иконку при завершении. Hide-on-close включается только после доступного
tray.start(), при отсутствии зависимости окно остаётся обычным. Ошибка
backend в уже запущенном потоке трея всё ещё требует отдельного handshake.

`AgentRunner.backup_now(destination)` требует работающий event loop,
сохраняет состояние и создаёт копию без await между ними. В этом же loop
следующий тик/обработчик не вмешается. Тест очередности подтверждает save,
copy, затем отложенный tick; ошибка save не запускает копию. Внешние процессы,
записи иных потоков и два разных SQLite-store не охвачены общей блокировкой.
API предназначен для вызова в потоке раннера, не для прямого вызова UI.
Остановка процесса остаётся предпочтительной для внешней CLI-копии.

Профильный прогон runner backup/runtime/recovery notice/UI/speed: 47 passed.

## Что ещё предстоит в этапах 0–1

1. Явный контекст хранения вместо процессного окружения при поддержке нескольких жизней.
2. Версионированная матрица durable/transient/inherited состояний.
3. Валидация всего восстанавливаемого объекта до публикации.
4. Проверенный комплект резервной копии, SQLite backup API, реальное восстановление.
5. Явный пользовательский отчёт/режим восстановления вместо traceback.
6. Согласованное закрытие/возобновление GUI, tray и runner.

Не заявляем этапы 0–1 завершёнными по одному исправленному сценарию.
