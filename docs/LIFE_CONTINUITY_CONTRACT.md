# Этапы 0–1: контракт непрерывности и безопасный запуск

## Правила, определяющие дальнейшую работу

- Один профиль данных предназначен одной жизни; разные имена чекпоинтов
  сами по себе не обеспечивают изоляцию отношений, LifeGuard и Delamain.
- Сохранённая история не является новой жизнью при ошибке её чтения.
- Новая жизнь допускается при отсутствии истории либо явном new/restore=False.
- Намерение, исполнение, наблюдение и достигнутая цель — разные события.
- Пауза и остановка приложения не должны обозначаться необратимым уходом.
- Основной чекпоинт — согласованный снимок уже включённых в него полей.
  Пока он не сохраняет всю индивидуальность: ценности, отношения, модели
  действий и другие выявленные пропуски предстоит подключить отдельно.
- JSON и SQLite — способы хранения, а не основания изменения опыта.
- Никакое расширение доступов не включается автоматически этим этапом.

## Первый реализованный участок: восстановление

Запуск перечисляет снимки нужного имени от новых к старым. Сохраняется
прежний приоритет SQLite перед JSON. Перечисление SQLite использует read-only
соединение и не создаёт/мигрирует схему. В JSON-кандидаты входят только
законченные .json/.json.gz, не временные файлы.

Если снимок не читается, проверяется следующий. Отчёт содержит
recovery_failures и recovered_from_older. Исходники не удаляются и не
карантинируются перемещением: оператор сохраняет доступ к повреждённым данным.
Если все снимки не читаются, возникает RecoveryRequiredError; приложение
не получает нового агента для запуска и автоматического сохранения.

Нечитаемая база, неподдерживаемая версия контейнера, более новая версия
состояния либо ошибка применения прекращают запуск. Ошибка применения
особенно важна: apply_state_to_agent пока не транзакционен для всего объекта,
поэтому продолжать подбор на частично изменённом агенте небезопасно.

Убрано безусловное knowledge.save() из bootstrap до восстановления.
Конструктор всё ещё инициализирует подсистемы и может создавать журналы:
гарантия здесь — не стартовать новую жизнь/не перезаписать снимки при
ошибке, а не полное отсутствие любых файловых операций во время запуска.

## Проверки

`tests/test_recovery_policy.py`: повреждённый последний JSON → предыдущий;
все повреждены → остановка; повреждённый SQLite manifest → предыдущий;
нечитаемая БД → остановка; временные файлы игнорируются. Проверяется отсутствие
перезаписи JSON-истории. Тест обычной ошибки load_state теперь требует
остановку, а не просто отсутствие ложной метки «восстановлен».

Профильный прогон: 44 passed (recovery, entry point, continuity, backend).
Это не новый общий прогон и не проверка собранного приложения.

## Что ещё предстоит в этапах 0–1

1. Единый data root до создания агента, в том числе frozen .exe.
2. Версионированная матрица durable/transient/inherited состояний.
3. Валидация всего восстанавливаемого объекта до публикации.
4. Проверенный комплект резервной копии, SQLite backup API, реальное восстановление.
5. Явный пользовательский отчёт/режим восстановления вместо traceback.
6. Согласованное закрытие/возобновление GUI, tray и runner.

Не заявляем этапы 0–1 завершёнными по одному исправленному сценарию.
