- **Планировщик** (`planner.py`): команды «запусти x.py» / run,
  «допиши в a.txt: …» / append, «создай папку» / mkdir.
- **Связка**: `DelamainRuntime(..., code_runner=None)`;

  `run_max_code_bytes` (env `DELAMAIN_RUN_*`, конфиг), строит
  `CodeRunner` в `_ensure_runtime`, показывает лимиты в `status()`.
- **Конфиг**: `DELAMAIN_APPROVAL_MODE = "dangerous"` (было `off`):
  с появлением run_python гейт включён — write_file, append_file,
  run_python, set_self_model, write_creative_draft ждут одобрения.

```text
begin_intention()
→ EffectorRequest
→ queued
→ waiting_approval
→ approve
→ agent.tick_subsystems()
→ succeeded и реальный файл
→ finish_intention()
→ _record_core_life_episode()
→ build_life_snapshot()
→ build_life_graph()
```

Terminal Effector result теперь автоматически замыкает когнитивное
intention только при явном `detail.metadata.intention_id`. Core завершает
только запись со статусом `started`, записывает один life episode и защищает
повторный terminal result. Результат без `intention_id`, а также `queued` и
`waiting_approval`, историю не меняют.

## Что делать дальше

v1 и этап 7 закрыты. Следующий разумный шаг — не новый экран и не миграция
стека, а приёмка и наблюдение:

1. повторно прогнать сквозной сценарий;
2. проверить restart continuity для intention, diary и Effector approval;
3. провести ручную 60–90-секундную демонстрацию:
   `Сейчас → approval → результат → Дневник → Карта жизни`;
4. записать фактическое поведение и ограничения;
5. только после этого решать, нужен ли отдельный v1.1.

Не начинать «вечный ремонт» визуала или Core без нового ограниченного
участка с критерием приёмки.

## Дневник: анти-мерцание и „свернуть“ (2026-11-02, закрыт, принят вручную)

Поверх UI-редизайна, по ручной приёмке пользователя (видео и скриншоты
мерцания Дневника). Обе партии — коммит 170b565, origin/main.
Причина найдена в коде: `_status_loop` в main.py
публикует снимок жизни каждые 0,5 с, а `_apply_diary_data` на каждом тике
безусловно сбрасывал `_diary_expanded`/`_diary_selected` и пересоздавал
(destroy+rebuild) все строки. Второй слой: раскрытие по «якорю» серии
(старейший эпизод) схлопывалось после тика — `recent_life_episodes`
держит скользящее окно (сортировка по id, `episodes[:limit]`), серии
уезжали из окна и якорь терялся.

Сделано (src/ui/main_window.py, src/ui/diary_view.py):

- Сигнатурная защита `_apply_diary_data`: перестройка строк только при
  фактическом изменении записей; защита `_apply_activity_data` —
  Listbox «Занятия» больше не теряет выделение на тиках; пустое
  состояние Дневника рисуется сразу при построении страницы.
- `group_key(episode)` в diary_view.py — кортеж содержания
  (action, target, status, outcome, error), единый источник для
  `group_diary_episodes` и UI. `_diary_expanded` хранит ключи
  содержания, поэтому раскрытие переживает сдвиг скользящего окна,
  рост серии и слияние серий.
- Кнопка «×N · свернуть» на головной строке развёрнутой серии
  (`_toggle_diary_group` + `_restore_diary_selection`); клик по
  головной строке при N>1 переключает серию по ключу содержания.

Известное ограничение: две серии с одинаковым содержанием
разворачиваются/сворачиваются вместе (ключ по содержанию, не по id).

## Проверенные практические особенности окружения

- Windows PowerShell: не использовать `&&` и shell heredoc `python - <<'PY'`;
- тесты не имеют права трогать реальные пути данных: только
  `data_path()`/корень изоляции из conftest; относительный
  `'data/checkpoints'` в cleanup-херпере теста однажды удалил все живые
  профили (гибель первой Тэсс);
- кириллица в stdout PowerShell может отображаться повреждённо — для проверки
  читать файлы или писать вывод в UTF-8;
- `deepcopy(agent.__dict__)` падает из-за `RLock`; сравнивать конкретные поля;
- `_intention_history`, `_waiting_intentions`, `_method_preferences` создаются
  лениво — читать через безопасный `_own()`;
- для теста отсутствующего Effector явно делать
  `agent.delamain_effector = None`;
- Tk-скриншот на Windows требует `root.attributes("-topmost", True)`;
- ImageGrab может захватить системную панель Task View — после съёмки
  визуально проверять кадры на системные оверлеи, пересъёмка в
  resume-режиме с Esc-очисткой оверлеев;
- полный набор без benchmarks занимает около 5 минут — не запускать его
  после каждого пробного редактирования, сначала использовать профильный набор.
